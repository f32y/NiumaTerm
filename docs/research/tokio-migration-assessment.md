**Tokio migration assessment — 2026-09-17**

Reviewed revision: `56623482` (`feat: move to tokio`). The lockfile resolves Tokio 1.53.1, mio 1.2.3, and reqwest 0.12.28. This is a source review of production paths in the first-party crates, with selected GPUI implementation checks. Tests were inspected as context where needed; no new runtime measurements or functional tests were performed for this assessment. No implementation changes accompany this report.

The strongest candidates are waiting-heavy Agent subprocess operations and the private runtimes and forwarding threads in remote sessions. UI execution, native rendering, CPU work, and durable storage should not be moved wholesale onto Tokio's four shared I/O workers.

**Yes** means a useful conversion to asynchronous waiting is available. **Conditional** means the surrounding ownership or ordering design must change first. **Blocking only** means Tokio could schedule the existing synchronous work, but would still occupy a blocking thread. **Keep** means the current execution model remains appropriate or has platform requirements that Tokio does not replace. P1 is the next useful work; P2 is follow-up work; P3 is low priority. These are recommendations, not measured speedup estimates.

The Windows PTY writer can migrate to Tokio, provided that native write completion remains observable independently of buffer acceptance.

The current ordering for input around a resize is:

```text
submit input A -> await native completion of A -> submit resize -> submit input B
```

[Termio's pending-command loop](../../crates/terminal/src/termio/mod.rs), lines 774–790, first waits for its queued input to be submitted, then calls the writer's `flush()` before executing a resize. [ConinPipe](../../crates/platform/src/windows/pipes.rs), lines 454–516, checks the overlapped operation, accounts for partial writes, and returns `WouldBlock` while a native write is still pending. Its completion notification causes the loop to try again. Output reads, generated terminal replies, and shutdown remain active during this wait.

Tokio's named-pipe writer has different behavior. The underlying mio writer can accept bytes into its own buffer and report success while the native write is pending. Consequently, completing `write_all().await` does not establish that all native writes have completed. Tokio's named-pipe `poll_flush` returns `Poll::Ready(Ok(()))` immediately, so an additional `flush().await` does not establish that condition either. This behavior is visible in the [mio writer](https://docs.rs/mio/1.2.3/src/mio/sys/windows/named_pipe.rs.html) and the [Tokio flush implementation](https://docs.rs/tokio/latest/src/tokio/net/windows/named_pipe.rs.html#918-924).

With a direct type replacement, input A could still be in flight when the resize call executes. That would weaken the existing input/resize ordering and could reintroduce timing-dependent input and redraw problems. Native write completion itself only establishes that the write operation finished; it does not acknowledge that ConPTY or the shell consumed or processed the input.

A migration therefore needs an explicit operation such as `wait_write_complete().await`, backed by completion state rather than ordinary flush success. Two possible directions are to adapt the current overlapped completion tracking to an async waiter, or to extend mio/Tokio with an observable native write-completion operation. The first can retain the existing wait callback; removing that callback as well requires a separate IOCP integration. Any implementation must retain each submitted buffer until native completion, handle partial writes and errors, and complete cancellation safely before releasing memory referenced by the operating system.

Validation must include a full pipe that leaves a write pending, a resize queued behind that write, peer closure during the wait, and shutdown with an outstanding write. The resize must remain pending until native completion is observed. The existing ConPTY typing/resize scenarios should also pass, with output and shutdown continuing to progress while input is blocked. This is a feasible migration with additional completion support, not an unsupported use of Tokio in principle.

A practical implementation order is:

1. Convert `DeadlineTimer` as a small independent change. In parallel planning, define task stop/completion behavior for remote sessions and remove the synchronous checkpoint wait and ConPTY creation from async worker execution.
2. Consolidate remote host/client/pair/list work onto `nmt_runtime`, then remove subscription and output forwarding threads while preserving bounded queues and snapshot ordering.
3. Introduce asynchronous Agent process I/O with platform process-tree ownership, then migrate title generation, DSH startup, CLI probes, and Git process waits.
4. Convert HTTP update paths and timer-driven log monitoring. Use the existing GPUI/Tokio bridge for UI-owned asynchronous operations and retain blocking stages explicitly.
5. Consider durable persistence and other background scheduling only where responsiveness or thread creation warrants it. Keep the previously deferred usage work as a separate item. Prototype a fully asynchronous PTY loop only after the ordering and throughput constraints are covered.

For UI-owned async work, the existing [GPUI bridge](../../third_party/gpui/gpui_tokio/src/gpui_tokio.rs), lines 55–70, aborts its Tokio task when the GPUI task is dropped. Preserve that behavior where cancellation is appropriate. Conversely, cleanup and durable-save tasks must not disappear with their view; they need explicit ownership until completion.

`spawn_blocking` is a scheduling tool for finite synchronous work, not a cancellation mechanism. Once such work starts, aborting its handle does not stop it. Persistent blocking loops should retain dedicated threads unless their waits are actually converted to async operations. CPU jobs also need a concurrency limit. These limits are documented in [Tokio's blocking-task guidance](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html). Child exit and descendant cleanup must remain explicit when adopting [Tokio process operations](https://docs.rs/tokio/1.53.1/tokio/process/index.html).

Validation for each implementation should exercise the changed ownership behavior: cancellation during startup, timeout after a mutation starts, cleanup after a view closes, remote slow consumers and checkpoint ordering, and process-tree exit. A PTY prototype additionally needs the existing real ConPTY typing/resize scenarios and separate idle, short-message, and sustained-output measurements. Thread counts estimated from source indicate where to measure; they do not establish an application-wide performance gain.
